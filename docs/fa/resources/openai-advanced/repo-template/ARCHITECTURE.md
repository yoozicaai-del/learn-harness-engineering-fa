## مدل لایه‌

از یک مدل جهت‌دار ثابت استفاده کنید تا عوامل معماری خودسرانه‌ای اختراع نکنند:

`Types -> Config -> Repo -> Service -> Runtime -> UI`

مسائل فراگیر باید از طریق مرزهای ارائه‌دهنده یا تطبیق‌کننده صریح وارد شوند، نه با رسیدن مستقیم به میان لایه‌ها.

## قوانین وابستگی سخت

- لایه‌های پایین‌تر نباید به لایه‌های بالاتر وابسته باشند.
- UI نباید قرارداد‌های Runtime یا Service را دور بزند.
- دسترسی به داده‌ها باید از طریق مخازن یا تطبیق‌کننده‌های معادل وارد شوند.
- ابزارهای مشترک باید عمومی بمانند و نباید منطق دامنه‌ای جمع کنند.
- وابستگی‌های جدید باید در طرح یا سند طراحی مطابقت توجیه شوند.

## چک لیست تغییر

وقتی به کد مرتبط با معماری دست می‌زنید:

1. اگر نقشه دامنه یا مرزهای مجاز تغییر کرده‌اند، این فایل را به‌روز کنید.
2. اگر استدلال تغییر کرده‌است، سند طراحی مرتبط در `docs/design-docs/` را به‌روز کنید.
3. اگر قانون باید به‌صورت مکانیکی تأیید شود، یک بررسی اجرایی اضافه یا به‌روز کنید.
