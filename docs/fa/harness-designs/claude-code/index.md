# تحلیل طراحی هارنس Claude Code

در مقالهٔ [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)، Anthropic به وضوح بیان می‌کند که قابل‌اعتماری از هارنس نه از مدل ناشی می‌شود، و اینکه ایجنت‌ها به محدودیت‌های «خارج از مدل» نیاز دارند. Claude Code نمونه‌ای تجاری از این ایده است؛ Anthropic خود صراحتاً آن را به عنوان یک **هارنس ایجنتی** طبقه‌بندی می‌کند. این زبان بازاریابی نیست—Claude Code شاید بیشترین بررسی عمومی را برای یک هارنس دیده است: کد منبع آن باز است، گزارش‌های تحقیقات جامعه تفصیلی است، و تقریباً هر مکانیزم اصلی در سخنرانی‌های دوره—حافظهٔ لایه‌ای، فشرده‌سازی متن، مجوزها، ربات‌های داخلی، و تداوم جلسه—را به یک پیاده‌سازی محصول کامل تبدیل می‌کند.

در این مقاله، از چارچوب پنج زیرسیستم دوره برای تحلیل Claude Code استفاده می‌کنیم، و بر روی نحوهٔ پیاده‌سازی مفاهیم بنیادی هارنس مانند «مدیریت متن»، «جلوگیری از اعلام زودهنگام تکمیل» و «محدودیت‌های تعیین‌کننده» تمرکز می‌کنیم.

## به یک جملهٔ خلاصه

در هسته Claude Code یک حلقهٔ while ساده است: مدل را فراخوانی کن، یک ابزار را اجرا کن، نتیجه را مشاهده کن، و مدل را دوباره فراخوانی کن. اما **اکثر کد در آن حلقه نیست؛ در سیستم‌های اطراف حلقه است**—سیستم مجوز، خط‌الرجع فشرده‌سازی متن، مکانیزم‌های توسعه، هماهنگ‌سازی ربات‌های داخلی، و ذخیرهٔ جلسه. این ماهیت یک هارنس است: حلقه اسکلت است، اما همه چیز اطراف اسکلت قابل‌اعتماری را تعیین می‌کند.

## زیرسیستم دستورالعمل: یک سیستم حافظهٔ لایه‌ای

سیستم حافظهٔ Claude Code کمک‌دهندگی مستقیم‌ترین آن به نظریهٔ هارنس است، و به سخنرانی‌های دوره درباره‌ی «ریپازیتوری به عنوان سیستم ثبت‌شدهٔ رسمی» و «تداوم متن بین جلسات» مربوط می‌شود. مستندات رسمی، [How Claude remembers your project](https://code.claude.com/docs/en/memory)، به وضوح بیان می‌کند که هر جلسه با پنجرهٔ متن تازهٔ شروع می‌شود و دانش را در میان جلسات از طریق دو مکانیزم حمل می‌کند: فایل‌های CLAUDE.md (دستورالعمل‌هایی که شما نوشته‌اید) و حافظهٔ خودکار (یادداشت‌هایی که Claude خود می‌نویسد).

در حوزهٔ دامنهٔ کار، مستندات رسمی فایل‌های CLAUDE.md را به چهار دستهٔ تقسیم می‌کند (از گسترده‌ترین تا مخصوص‌ترین بارگذاری):

- **سطح سیاست سازمانی**: توسط IT/DevOps مرکزی مدیریت می‌شود (برای مثال، `/etc/claude-code/CLAUDE.md`) برای استانداردهای سراسری شرکت.
- **سطح کاربر `~/.claude/CLAUDE.md`**: ترجیحات شخصی و قوانینی که در تمام پروژه‌ها اعمال می‌شود.
- **سطح پروژه `./CLAUDE.md` یا `./.claude/CLAUDE.md`**: سیستم ثبت‌شدهٔ رسمی پروژه برای معماری، کوچهٔ فناوری، و دستورات راستی‌آزمایی، که با ریپازیتوری مشترک است.
- **سطح محلی `./CLAUDE.local.md`**: ترجیحات شخصی درون یک پروژه، معمولاً به `.gitignore` اضافه می‌شود تا اضطر نشود.

دو مکانیزم اضافی نیز وجود دارد:

- **بارگذاری درخواستی در سطح زیردایرکتوری**: فایل‌های CLAUDE.md در زیردایرکتوری‌ها در راه‌اندازی بارگذاری نمی‌شود؛ آن‌ها تنها زمانی وارد متن می‌شود که Claude فایل‌ها را در آن دایرکتوری بخواند.
- **حافظهٔ خودکار**: Claude فعالانه یادداشت‌ها را بر اساس اصلاحات و ترجیحات شما می‌نویسد. این یادداشت‌ها توسط ریپازیتوری مشترک است، در تمام worktree ها اعمال می‌شود، و حداکثر ۲۰۰ خط یا ۲۵KB در هر جلسه بارگذاری می‌شود.

این چهار دامنهٔ کار یک **سلسله‌مراتب دستورالعمل** تشکیل می‌دهد: مستندات رسمی می‌گویند که «دستورالعمل‌های مخصوص‌تر بعداً در متن ظاهر می‌شوند» (دستورالعمل‌های پروژه پس از دستورالعمل‌های کاربر ظاهر می‌شود). ارزش این است که مدل مجبور نیست تمام فایل دستورالعمل‌های غول‌آسا را در آغاز هر گفتگو هضم کند؛ دستورالعمل‌ها نزدیک به جایی که اعمال می‌شوند بارگذاری می‌شوند، بر اساس دامنهٔ کار. این پاسخ تجاری به سخنرانی ۴، «چرا یک فایل دستورالعمل غول‌آسا شکست می‌خورد» است.

## زیرسیستم متن: یک خط‌الرجع فشرده‌سازی پنج لایه‌ای

Claude Code متن را از طریق یک **خط‌الرجع فشرده‌سازی پنج لایه‌ای** مدیریت می‌کند، نه صرفاً با «خلاصه کردن هنگام پر شدن». این جزئیات معماری از تجزیهٔ سطح منبع VILA Lab، [Dive into Claude Code](https://zhiqiangshen.com/projects/Claude_Code_Report/Claude_Code_Report.pdf)، آمده است. سخنرانی ۵ توضیح می‌دهد که چگونه کارهای درازمدت تداوم را از دست می‌دهند؛ پاسخ Claude Code یک ترشح چند‌مرحله‌ای است: ابتدا تخلیهٔ بدون اتلاف (حذف نتایج ابزار تکراری) را اعمال کن، سپس فشرده‌سازی ساختاری را انجام دهید، و تنها پس از آن خلاصه‌های LLM با اتلاف استفاده کنید، با قطع‌کننده‌های مدار برای جلوگیری از فشرده‌سازی بیش‌ازحد.

این با طراحی ذخیرهٔ جلسه جفت می‌شود: **ذخیرهٔ جهت‌افزودنی**. تمام تاریخ به `history.jsonl` افزوده می‌شود، با بازیابی `/resume` و شاخه‌های انشعاب. این تضمین می‌کند که «هر جلسه قبل از پایان تحویل خوبی را انجام می‌دهد»—نه به این دلیل که سیستم حافظهٔ خوبی دارد، بلکه به دلیل اینکه لایهٔ ذخیره‌سازی جهت‌افزودنی و قابل‌بازپخش است.

## زیرسیستم ابزار: چهار مکانیزم توسعه

Claude Code سطح توسعهٔ خود را به چهار دسته تقسیم می‌کند، هر کدام یک مسئلهٔ متفاوت را حل می‌کند. این بخشی از طراحی است که بیشترین ارزش را برای تقبل دارد:

- **مهارت‌ها**: در [مستندات رسمی](https://code.claude.com/docs/en/skills) به عنوان دانش رویه‌ای توصیف‌شده توسط `SKILL.md` تعریف‌شده، خودکار بر اساس ماشه‌ها از طریق افشا تدریجی بارگذاری‌شده. آن‌ها برای دانش حوزه‌ای درباره‌ی «چگونه انجام دادن کاری» مناسب هستند.
- **MCP**: پروتکل JSON-RPC در [مستندات رسمی](https://code.claude.com/docs/en/mcp) سیستم‌های خارجی را متصل می‌کند، رابطی استاندارد را فراهم می‌کند که از طریق آن «مدل می‌تواند به دنیای بیرونی برسد».
- **ربات‌های داخلی**: اسکریپت‌های تعیین‌کننده‌ای متصل به رویدادهای چرخهٔ حیات مانند `PreToolUse`، `PostToolUse`، و `Stop`، همانگونه که در [مستندات رسمی](https://code.claude.com/docs/en/hooks) توضیح داده‌شده است.
- **افزونه‌ها / ربات‌های داخلی**: [مستندات رسمی](https://code.claude.com/docs/en/sub-agents) تفویض‌کردن کارهای پیچیده به ایجنت‌های تخصصی را توصیف می‌کند.

طراحی کلیدی **تفکیک مسئولیت‌ها** است: CLAUDE.md «چه» را مدیریت می‌کند، مهارت‌ها «چگونه» را مدیریت می‌کند، MCP «کجا اتصال» را مدیریت می‌کند، و ربات‌های داخلی «کی اجرا» را مدیریت می‌کند. اگر تیم این لایه‌ها را با هم مخلوط کند—برای مثال، قرار دادن کاری که به MCP تعلق دارد در CLAUDE.md—متن نشتی‌ای را که در دوره توضیح داده‌شده است ایجاد می‌کند.

## بازخورد و راستی‌آزمایی: محدودیت‌های تعیین‌کننده + تقسیم کار انسان و ایجنت

سخنرانی ۱۰ توضیح می‌دهد که «راستی‌آزمایی تنها هنگامی اهمیت دارد که تمام جریان کار». Claude Code این را از طریق دو مسیر پیاده‌سازی می‌کند:

**۱. سیستم مجوز (محدودیت‌های تعیین‌کننده).** مجوزهای Claude Code صرفاً «درباره‌ی همه چیز پرسش نکن». آن‌ها هفت حالت را با یک طبقه‌بندی‌کنندهٔ مبتنی‌بر ML ترکیب می‌کند: عملیات ریسک کم مجاز هستند، در حالی که عملیات ریسک زیاد یا تایید می‌شود یا بر اساس سیاست رد می‌شود (برای جزئیات معماری، [تجزیهٔ VILA Lab](https://zhiqiangshen.com/projects/Claude_Code_Report/Claude_Code_Report.pdf) را ببینید). این «تعیین مرزهای واضح برای ایجنت» (سخنرانی ۷) را از یک درخواست در پرامپت به اجرای زمان‌اجرا تبدیل می‌کند.

**۲. ربات‌های داخلی (جلوگیری از اعلام زودهنگام تکمیل).** ربات‌های `PostToolUse` می‌توانند بررسی‌ها را بعد از اجرای ابزار اجبار کنند و نتایج را دوباره در متن بنویسند؛ ربات‌های `Stop` وقتی ایجنت تکمیل را اعلام می‌کند مداخله می‌کند. این «کسی که کار را انجام می‌دهد» را از «کسی که کار را بررسی می‌کند» جدا می‌کند. [Anthropic صراحتاً در مقالهٔ هارنس خود مشاهده کرد](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) که ایجنت‌ها «با اطمینان از کار خود ستایش می‌کردند»، بنابراین ربات‌های داخلی بررسی‌های **تعیین‌کننده** را تزریق می‌کند نه اینکه به خود‌ارزیابی مدل اعتماد کنند.

**۳. ربات‌های داخلی (ایزوله‌سازی متن).** تاریخ مکالمهٔ هر ربات داخلی در فایل sidechain جداگانه‌ای ذخیره می‌شود و **متن ایجنت والد را بالا نمی‌برد** ([تجزیهٔ VILA Lab](https://zhiqiangshen.com/projects/Claude_Code_Report/Claude_Code_Report.pdf) را ببینید). این «مرزهای کار» را با «ایزوله‌سازی آلودگی متن» ترکیب می‌کند: تقسیم‌کردن کار نیز متن را ایزوله می‌کند.

## رصدپذیری و تداوم جلسه

سیاهه‌های Claude Code رکوردهای جهت‌افزودنی کامل (history.jsonl) هستند. همراه با دستورات صریح مانند `/compact`، `/clear`، و `/init`، این به شما اجازه می‌دهد وضعیت متن را به فعال‌انه مدیریت کنید نه اینکه منفعلانه برای پر شدن منتظر بمانید. `/init` حتی «مقدماتی کردن قبل از شروع هر کار توسط ایجنت» (سخنرانی ۶) را به یک دستور تبدیل می‌کند. [مستندات رسمی](https://code.claude.com/docs/en/memory) می‌گویند که خودکار ریپازیتوری را تجزیه می‌کند و یک CLAUDE.md اولیهٔ شامل فرمان‌های ساخت، دستورات آزمایش، و قراردادهای مهندسی را تولید می‌کند.

| --- | --- | --- |
| دستورالعمل‌ها | دامنه‌های لایه‌ای (سازمانی/کاربر/پروژه/محلی) + حافظهٔ خودکار | حافظهٔ لایه‌ای معیار پیاده‌سازی است |
| ابزارها | چهار نوع توسعه: مهارت‌ها + MCP + ربات‌های داخلی + ربات‌های داخلی | تفکیک روشن مسئولیت‌ها نقطهٔ قوت اصلی است |
| محیط | تنظیمات درون‌پروژه + settings.json | بر کاربران متکی است تا محیط را در CLAUDE.md توصیف کنند |
| وضعیت | ذخیرهٔ جلسهٔ جهت‌افزودنی + فشرده‌سازی پنج لایه‌ای + بازیابی/انشعاب | بسیار قوی؛ یک پیاده‌سازی مرجع برای تداوم کار درازمدت |
| بازخورد | طبقه‌بندی‌کنندهٔ مجوز + بررسی‌های اجباری از طریق ربات‌های `PostToolUse` | «جلوگیری از اعلام زودهنگام تکمیل» را به یک مکانیزم تعیین‌کننده تبدیل می‌کند |

## طراحی‌هایی شایستهٔ تقبل

۱. **دستورالعمل‌ها را بر اساس دامنهٔ کار لایه‌بندی کنید** نه اینکه آن‌ها را در یک فایل منفرد انباشته کنید. فایل‌های CLAUDE.md در سطح دایرکتوری پیاده‌سازی الگان «بارگذاری نزدیک به جایی که دستورالعمل‌ها اعمال می‌شوند» هستند.
۲. **فشرده‌سازی باید یک ترشح مرحله‌ای باشد**: بدون اتلاف قبل از اتلاف؛ از خلاصه‌کردن همه چیز شروع نکنید.
۳. **برای بررسی‌های تعیین‌کننده از ربات‌های داخلی استفاده کنید**: جلوگیری از اعلام زودهنگام تکمیل به اجرای زمان‌اجرا نیاز دارد، نه درخواست در پرامپت‌ها.
۴. **متن ربات داخلی را ایزوله کنید**: متن را هنگام تقسیم‌کردن کار تقسیم کنید تا نتایج کار فرعی متن حلقهٔ اصلی را آلوده نکند.
۵. **ذخیرهٔ جلسه را جهت‌افزودنی و قابل‌بازپخش کنید**: تحویل‌ها به لایهٔ ذخیره‌سازی بستگی دارند، نه به حافظه.
