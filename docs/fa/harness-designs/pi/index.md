# تحلیل طراحی هارنس Pi

[Pi](https://pi.dev/) (بسته npm `@earendil-works/pi-coding-agent`) خود را «هارنس کمینه» معرفی می‌کند. این عبارت شایسته‌ی بررسی دقیق است: خود را «قوی‌ترین ایجنت کدنویسی» یا «بهترین ابزار برنامه‌نویسی هوش مصنوعی» نمی‌خواند. در عوض، هویت خود را به محکمی در کلمه **هارنس** متصل می‌کند.

در این مقاله، از چارچوب پنج زیرسیستمی دوره—دستورالعمل‌ها، ابزارها، محیط، وضعیت، و بازخورد—برای بررسی Pi و شناسایی نحوه‌ی تفاوت اساسی فلسفه‌ی طراحی آن از Claude Code و Codex استفاده می‌کنیم. پاسخ از پیش‌رو است: **فلسفه‌ی Pi این است که «هسته را کمینه کن + افزونه‌ها را برنامه‌پذیر کن.» این رویکرد مهندسی بافت را فراتر از پرامپت سیستمی می‌برد و به کاربران—حتی خود Pi—اجازه می‌دهد هارنس را تغییر دهند، به‌جای اینکه Pi تصمیم بگیرد.**

## خلاصه در یک جمله

Pi یک هسته‌ی کمینه است: موقعیت‌گیری رسمی آن عمداً هسته را کوچک نگاه می‌دارد و کنترل را به شما می‌دهد. بر اساس گفته‌های [صفحه‌ی اصلی pi.dev](https://pi.dev/)، «از Pi بخواهید آنچه می‌خواهید بسازید یا بسته‌ای نصب کنید که به روش شما کار کند.» هارنس را به چهار لایه‌ی سفارشی‌پذیر تقسیم می‌کند:

- **افزونه‌ها**: قوچ‌های TypeScript که به رویدادهای چرخه‌ی حیات Pi متصل هستند و سطح برنامه‌پذیری را در سطح زمان‌اجرا فراهم می‌کنند.
- **مهارت‌ها**: بسته‌های قابلیت درخواستی حاوی دستورالعمل‌ها و ابزارها، با استفاده از افشای تدریجی.
- **الگوهای پرامپت**: پرامپت‌های Markdown قابل‌استفاده‌ی مجدد که هنگام وارد کردن `/name` بسط می‌یابند.
- **تم‌ها**: ظاهر رابط TUI.

این رویکرد لایه‌ای خود شکلی از مهندسی هارنس است: **قوانین و افزونه‌ها کاملاً تعیین می‌کنند که مدل چه می‌تواند ببیند و چه زمانی می‌تواند ببیند، به‌جای اینکه این تصمیمات در هسته‌ی اصلی سخت‌افزار شده باشند.**

## حلقه‌ی اصلی

مانند هر ایجنت کدنویسی، Pi اساساً یک حلقه‌ی while از «استدلال → اجرای ابزار → مشاهده → استدلال بیشتر» است. آنچه اهمیت دارد نه خود حلقه است، بلکه نحوه‌ی رسیدگی Pi به لایه‌ی اطراف آن است: مهندسی بافت را از «فشرده‌سازی» درون حلقه تا «کنترل» بیرون حلقه گسترش می‌دهد.

زمان‌اجرای Pi یک رابط برنامه‌پذیر را فاش می‌کند. علاوه‌بر یک رابط TUI تعاملی، [بخش Programmatic Usage صفحه‌ی README اصلی](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md) از حالت‌های چاپ/JSON اسکریپت‌پذیر، پروتکل RPC، و جاسازی SDK حمایت می‌کند. این بدان معنی است که همان هارنس می‌تواند توسط انسان گام‌به‌گام یا خودکار توسط CI/CD یا برنامه‌ای دیگر راه‌انداز شود. این پیش‌نیاز برای حرکت «از کنترل دستی به حلقه‌های خودکار» که در سخنرانی 13 درباره‌ی مهندسی حلقه توضیح داده شده است را فراهم می‌کند: یک هارنس که فقط می‌تواند به‌صورت تعاملی توسط انسان‌ها راه‌انداز شود هرگز نمی‌تواند وارد حلقه‌ی خودکار شود.

## زیرسیستم دستورالعمل: AGENTS.md و SYSTEM.md

Pi در نحوه‌ی رسیدگی به دستورالعمل‌ها محتاط است، اما سلسله‌مراتب آن واضح است:

- **AGENTS.md**: [بخش Project Context Files صفحه‌ی README اصلی](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md) به‌طور صریح ترتیب بارگذاری را مستند می‌کند: `~/.pi/agent/AGENTS.md` سراسری → رفتن به‌بالا در فهرست‌های والد سطح‌به‌سطح → `./AGENTS.md` فهرست‌ی جاری (همچنین با سازگاری CLAUDE.md). این «مخزن به‌عنوان نقطه‌ی مرجع سیستم» را عملی می‌کند—دستورالعمل‌ها فایل‌ها هستند، نه یادآوری‌هایی که در صندوق گفتگو تایپ می‌شوند.
- **SYSTEM.md**: [مستندات رسمی pi.dev](https://pi.dev/docs/usage/project-context) می‌گویند که پرامپت سیستم پیش‌فرض می‌تواند هر پروژه را جایگزین یا اضافه شود. این تنها نقطه‌ی ورود رسمی Pi برای تغییر «پرامپت سیستم» است و همچنین به‌عنوان لایه‌ی «توصیف‌ خود محیط» آن نقش دارد.

Pi رسماً تأکید می‌کند که پرامپت سیستم آن **کمینه** است. این منعکس‌کننده‌ی یک تعادل صریح است: هسته‌اصلی فهرست‌های طولانی از قوانین «اگر...آنگاه...» را بسته‌بندی نمی‌کند. در عوض، نقاط افزونه‌ای را فاش می‌کند تا قوانین تنها وقتی مورد نیاز هستند به‌عنوان مهارت‌ها و افزونه‌ها ظاهر شوند. این مستقیماً سخنرانی 4، «چرا یک فایل دستورالعمل بزرگ شکست می‌خورد»—را تکرار می‌کند. Pi طبیعی‌طور این مسئله را از طریق رویکرد «هسته‌ی کمینه + تقسیم فایل‌ها + بارگذاری درخواستی» جلوگیری می‌کند.

## وضعیت و بافت: جایی که Pi بیشترین دقت را دارد

مهندسی بافت Pi شایسته‌ی توجه خاص است زیرا مفاهیمی مانند «تداوم بافت» و «جلوگیری از خرابی بافت» دوره را به مکانیزم‌های عینی تبدیل می‌کند:

**۱. فشرده‌سازی برنامه‌پذیر.** همان‌طور که حد بافت نزدیک می‌شود، پیام‌های قدیمی‌تر خودکار خلاصه می‌شوند. [مستندات رسمی pi.dev](https://pi.dev/docs/usage/sessions) توضیح می‌دهد که استراتژی فشرده‌سازی خود **سفارشی‌پذیر** است: می‌توانید برای پیاده‌سازی فشرده‌سازی مبتنی‌بر موضوع، خلاصه‌های آگاه‌شده‌ی کد، یا حتی استفاده از مدل متفاوتی برای خلاصه‌سازی از افزونه‌ها استفاده کنید. صفحه‌ی README اصلی همچنین جزئیات مکانیزم پیش‌فرض را فاش می‌کند: فشرده‌سازی خودکار در دو مورد (بازیابی از سرریز بافت / تجاوز آستانه‌ی نگهداری) راه‌انداز می‌شود، نقطه‌ی تقسیم تقریباً ۲۰،۰۰۰ توکن اخیر را حفظ می‌کند، و پیام‌های پیشین در یک «تحویل جلسه» خلاصه‌شده و به‌صورت تدریجی در یک زنجیر فشرده می‌شوند. به‌عبارت دیگر، Pi نحوه‌ی فشرده‌سازی بافت را نه به‌عنوان ثابت سخت‌افزار شده، بلکه به‌عنوان بخشی از هارنس در نظر می‌گیرد.

**۲. بافت پویا.** [مستندات رسمی pi.dev](https://pi.dev/docs/usage/extensions) می‌گویند افزونه‌ها می‌توانند پیام‌ها را قبل از هر دور استدلال تزریق کنند، تاریخ پیام را فیلتر کنند، RAG را پیاده‌سازی کنند، و حافظه‌ی بلندمدت بسازند. این فراتر از «فشرده‌سازی هنگامی که بافت پر است» است: به‌شما اجازه می‌دهد تصمیم بگیرید چه چیزی قبل از ورود به پنجره‌ی بافت در بافت وارد شود. از نظر اهداف دوره‌ی «کردن اجرای عامل قابل‌مشاهده و قابل‌اشکال‌زدایی» و «نگهداری تداوم بافت»، Pi هر دو را به سطح افزونه فشار می‌دهد.

**۳. درخت جلسه.** [صفحه‌ی اصلی pi.dev](https://pi.dev/) به‌طور صریح می‌گویند «جلسات به‌عنوان درخت ذخیره می‌شوند»؛ `/tree` می‌تواند به هر گره تاریخی برگردد و از آنجا ادامه دهد، با هر شاخه در همان فایل ذخیره شود. این به شکاف‌های بافت متقاطع جلسه‌ای پاسخ می‌دهد که مکرراً در دوره تأکید شده است—نه با اجبار خلاصه‌ها برای پل‌زدن شکاف، بلکه از طریق تکرار تاریخ ساخت‌یافته. شاخه‌ها می‌توانند به‌صورت HTML صادر شوند یا به‌عنوان gist بارگذاری شوند برای اشتراک، که همچنین رصدپذیری را فراهم می‌کند.

## زیرسیستم ابزار: مهارت‌ها و افزونه‌ها

«ابزارهای» Pi دو لایه دارند:

- **مهارت‌ها**: [بخش Skills صفحه‌ی README اصلی](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md) این‌ها را به‌وضوح به‌عنوان «بسته‌های قابلیت خودمختار که عامل درخواستی بارگذاری می‌کند» تعریف می‌کند. آن‌ها دستورالعمل‌ها و ابزارها را شامل می‌شوند و از استاندارد Agent Skills پیروی می‌کنند. افشای تدریجی تضمین می‌کند که جزئیات مهارت تنها هنگام فعال‌شدن وارد بافت شود، **بدون تأثیر منفی بر کش پرامپت**. این مهندسی هارنس از دیدگاه هزینه است: هر توکن اضافی در بافت باید برای هر استنتاج پرداخت شود. بارگذاری مهارت‌ها درخواستی بیان دیگری از «نقشه را بده، نه کتاب راهنمای مکمل» است.
- **افزونه‌ها**: قوچ‌های TypeScript که به رویدادهای چرخه‌ی حیات داخلی متصل هستند. [بخش Hooks صفحه‌ی README اصلی](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md) نمونه‌های رسمی را می‌دهد: رهگیری دستورات خطرناک (دروازه‌ی مجوز)، ایجاد چک‌پوینت وضعیت کد هنگام تبدیل وظایف، محافظت از مسیرها (برای مثال، ممنوعیت نوشتن در `.env`)، اصلاح خروجی ابزار قبل از انتقال به مدل، و تزریق پیام‌ها از منابع خارجی (دیدبان‌های فایل/وبها/CI) برای بیدار کردن عامل. این API‌های قوچ همچنین از `@mariozechner/pi-coding-agent/hooks` صادر می‌شوند. هارنس اجتماعی [pi-agent-harness](https://github.com/LabidySabidy/pi-agent-harness) این سطح قوچ را بیشتر در افزونه‌های آماده مانند skill-router، session-summary، extract-patterns، و telemetry بسته‌بندی می‌کند.

افزونه‌ها مهم‌ترین تصمیم طراحی Pi هستند: **به‌جای تنها دادن تعداد کمی تغییرپذیر به کاربران، Pi کل سطح رویداد درون زمان‌اجرا را فاش می‌کند.** می‌خواهید حافظه اضافه کنید؟ آن را در `agent/pre-step` تزریق کنید. می‌خواهید رفتار ثبت کنید؟ به رویدادهای جلسه مشترک شوید. می‌خواهید درخواست مدل را تغییر دهید؟ به `agent/request` قوچ کنید. می‌توانید Pi را تغییر هارنس خود کند—این بیشتر به تعریف یک «هارنس برنامه‌پذیر» نزدیک می‌شود تا هر مجموعه‌ای از گزینه‌های پیکربندی.

## بازخورد و راستی‌آزمایی: کردن «یادگیری» بخشی از هارنس

Pi خود شامل دروازه‌های تست اجباری نیست (کاربران باید دستورات تایید را در AGENTS.md مشخص کنند)، اما هارنس اجتماعی [pi-agent-harness](https://github.com/LabidySabidy/pi-agent-harness) از افزونه‌ها برای ساختار «حلقه‌ی بازخورد» استفاده می‌کند. بخش Hooks صفحه‌ی README رسمی بنیاد برای مکانیزم‌های مشابهی فراهم می‌کند:

- **session-summary** (افزونه‌ی pi-agent-harness): نوشته‌های `PROGRESS.md` غلتان را نگهداری می‌کند—زیرسیستم وضعیت دوره، برای ردیابی پیشرفت در وظایف بلندمدت.
- **extract-patterns** (افزونه‌ی pi-agent-harness): درس‌های نامزد را از جلسات جمع‌آوری می‌کند و در `LESSONS.md` ثبت می‌کند—تبدیل «رها کردن یک تحویل خوب قبل از پایان هر جلسه» از یک اصطلاح به یک مکانیزم.
- **telemetry** (افزونه‌ی pi-agent-harness): استفاده از توکن، هزینه، و معیارهای مرتبط را ثبت می‌کند—رصدپذیری.

مخزن اجتماعی یکسان الگو را بیشتر نشان می‌دهد: `VISION.md` (اهداف)، `PROGRESS.md` (پیشرفت)، `LESSONS.md` (درس‌ها)، و `STANDARDS.md` (استاندارد‌ها) همگی فایل‌های Markdown پایدار برای جلسات هستند. این دقیقاً «مخزن به‌عنوان نقطه‌ی مرجع سیستم + فایل‌های پیشرفت + مکانیزم تحویل» است که توسط دوره توصیه‌شده است، از طریق مکانیزم افزونه‌ی Pi به‌طور خارج‌از‌صندوق دسترس‌پذیر.

## نقشه‌برداری به چارچوب دوره

امتیازدهی Pi با پنج زیرسیستم دوره (ذهنی، برای مقایسه):

| زیرسیستم | پیاده‌سازی Pi | ارزیابی |
| --- | --- | --- |
| دستورالعمل‌ها | بارگذاری سلسله‌مراتبی AGENTS.md + SYSTEM.md | سلسله‌مراتب واضح، اما کاربران باید قوانین را خود بنویسند |
| ابزارها | مهارت‌های درخواستی + قوچ‌های چرخه‌ی حیات کامل | فوق‌العاده قوی؛ سیستم ابزار را به سطح برنامه‌پذیر تبدیل می‌کند |
| محیط | SYSTEM.md برای توصیف خود محیط؛ کاربران محیط زمان‌اجرا را در AGENTS.md تعریف می‌کنند | مکانیزم باز است، اما قابل‌تکرارپذیری بستگی به توصیف‌های کاربر دارد |
| وضعیت | درخت جلسه + فشرده‌سازی سفارشی‌پذیر + PROGRESS.md | فوق‌العاده قوی؛ تداوم متقاطع جلسه و بازیابی‌پذیری در مرکز هستند |
| بازخورد | دستورات تایید تعریف‌شده‌ی کاربر؛ مکانیزم‌های جلسه‌خلاصه‌ی ساخت‌یافته / extract-patterns | مکانیزم فراهم‌شده است؛ کاربران محتوا را تامین می‌کنند |

تعادل‌های Pi به شدت در تقابل با Claude Code و Codex هستند. Claude Code «حافظه، مجوزها، و زیرعامل‌ها» را درون هسته برای تجربه‌ی خارج‌از‌صندوق می‌گذارد؛ Codex «اصطلاحات مخزن و جداسازی محیط» را پیش‌فرض‌ها می‌کند. Pi انتخاب می‌کند **برای شما تصمیم‌گیری نکند**—تصمیم‌ات را به نقاط افزونه تبدیل می‌کند. هزینه این است که باید یا خود افزونه‌ها را بنویسید یا بسته‌هایی که دیگران نوشته‌اند را نصب کنید.

## طراحی‌های شایسته‌ی پذیرش

۱. **استراتژی فشرده‌سازی را متصل‌کن.** «چگونه بافت فشرده می‌شود» در هارنس خود نباید پارامتر سخت‌افزار‌شده باشد؛ باید رابط استراتژی جایگزین‌پذیر باشد.
۲. **درخت جلسه را به‌جای خلاصه‌های اجباری استفاده کن.** بازیابی متقاطع جلسه نیازی برای «خلاصه‌ی نوبت پیشین» ندارد؛ تکرار تاریخ ساخت‌یافته اغلب زیرسیستم وضعیت قابل‌اعتمادتری است.
۳. **کش پرامپت را دوست بدار.** مهارت‌ها را درخواستی بارگذاری کن به‌جای قرار دادن هر قانون در پرامپت سیستم یکباره. این هم مهندسی بافت است و هم مهندسی هزینه.
۴. **اجازه بده که عامل هارنس خود را تغییر دهد.** اگر هارنس نقاط افزونه‌ی کافی را فاش کند، بهینه‌سازی رفتار عامل خود می‌تواند تا حدی توسط خود عامل خودکار شود.

## منابع (منابع اصلی / کد منبع)

هر ادعا می‌تواند به منابع اصلی یا کد منبع زیر ردگیری شود، جلوگیری از یادآوری غیرمستقیم:
